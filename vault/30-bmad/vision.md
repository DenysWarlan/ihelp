# "Є турбота" — Care Coordination Platform

> Це не CRM. Це платформа координації турботи про людей.

---

## 1. Філософія проекту

### Чому не CRM?

CRM = **Customer Relationship Management** — це про продажі, воронки, угоди, гроші.
Ваш проект — не про продажі. Це про **турботу про людей**.

| CRM-мислення | Care-мислення |
|---|---|
| "Лід" | **"Людина, якій потрібна допомога"** |
| "Угода" | **"Кейс / історія супроводу"** |
| "Воронка продажів" | **"Шлях відновлення"** |
| "Конверсія" | **"Прогрес людини"** |
| "Менеджер" | **"Душеопікун / консультант"** |
| "Закрити угоду" | **"Людина відновлена / передана / продовжує шлях"** |

### Що ближче за моделлю

| Модель | Суть | Приклади |
|---|---|---|
| ~~CRM~~ | Воронка продажів | Pipedrive, HubSpot |
| **Case Management** | Ведення кейсів людей: статус, відповідальний, історія, нотатки | Соцслужби, психологічні центри |
| **Care Coordination Platform** | Координація турботи: клієнт → консультант → план → зустрічі → прогрес | Медицина, менторство, душеопікунство |
| Helpdesk / Ticketing | Звернення → призначення → вирішення | Freshdesk, Zendesk |

**"Є турбота" — це Care Coordination Platform.**

## 2. Технічний стек

```
Frontend:     Angular 19 + Angular Material / PrimeNG
Backend:      NestJS (TypeScript)
БД:           PostgreSQL
ORM:          Prisma або TypeORM
Чат:          Socket.io (веб) + Unified Message Bus (омніканал)
Авторизація:  JWT + Guards
Файли:        S3 / Cloudflare R2
Відео:        Zoom SDK / Google Calendar API
Лендинг:      Окремо на Astro або Angular Universal (SSR)
Месенджери:   Telegram Bot API, Instagram Messaging API, Facebook Messenger, Viber Bot API
```

## 4. Ролі в системі

| Роль | Що бачить | Що може |
|---|---|---|
| **Людина (Person)** | Свій кабінет, свого консультанта, свої курси | Писати консультанту, проходити курси, планувати зустрічі |
| **Консультант** | Тільки свої кейси | Вести переписку, робити нотатки, планувати зустрічі, бачити прогрес курсів |
| **Супервізор** | Переписки всіх консультантів (read-only), звіти якості | Залишати приватні коментарі консультантам, проводити розбори кейсів, контроль кризового протоколу |
| **Координатор** | Дашборд, винятки, аналітика навантаження | Ручне призначення у складних випадках, підтримка команди, аналіз трендів |
| **Адміністратор** | Все | Управління користувачами, курсами, налаштуваннями, автоматизаціями |

## 5. Три шляхи входу людини

### Путь А: "Мені потрібна допомога"

```
Людина бачить рекламу / сайт / пост
        ↓
Заходить на лендинг "Є турбота"
        ↓
Натискає "Отримати підтримку"
        ↓
Заповнює анкету (ім'я, тема, терміновість)
        ↓
Створюється Care Case → координатор бачить
        ↓
Координатор призначає душеопікуна
        ↓
Душеопікун пише перше повідомлення
        ↓
Переписка → зустріч (Zoom/Meet) → курс
        ↓
Супровід → прогрес → завершення або передача
```

### Путь Б: "Хочу пройти курс"

```
Людина бачить рекламу курсу
        ↓
Реєструється → починає проходити уроки
        ↓
Ніякого консультанта поки немає — просто вчиться
        ↓
На уроці 3 щось зачепило
        ↓
Натискає "Поговорити з консультантом"
        ↓
Коротка міні-анкета (профіль вже є)
        ↓
Care Case створюється з контекстом:
  - який курс проходить
  - який урок зараз
  - що саме зачепило
        ↓
Координатор призначає консультанта
        ↓
Консультант бачить контекст і починає розмову не з нуля
```

### Путь В: Курс без звернення

```
Людина пройшла курс → не натиснула "поговорити"
→ завершила → побачила наступний курс → пройшла
→ може колись звернеться, може ні
```

Система фіксує аналітику: скільки людей проходять курси, скільки потім звертаються за підтримкою.

### Повна схема

```
                     Є турбота
                    ┌──────────┐
                    │ Лендинг  │
                    └────┬─────┘
                   ┌─────┴──────┐
                   ↓            ↓
            "Підтримка"    "Курси"
                   ↓            ↓
              Анкета      Реєстрація
                   ↓            ↓
             Care Case     Проходить курс
                   ↓            ↓
            Консультант    Уроки 1, 2, 3...
                   ↓            ↓
              Переписка    "Хочу поговорити"
                   ↓            ↓
               Зустріч     Care Case → Консультант
                   ↓            ↓
                   └─────┬──────┘
                         ↓
                   Супровід
                 (курс + консультант)
```

## 6. Омніканальний чат

### Принцип

Людина спілкується там, де їй зручно (Telegram, Instagram, сайт). Консультант працює в одному інтерфейсі. Система маршрутизує повідомлення автоматично.

### Архітектура

```
                        ┌─────────────────────────┐
  Сайт (Socket.io) ────→│                         │
  Telegram Bot API ────→│   Unified Message Bus   │──→ Care Case
  Instagram API ───────→│     (NestJS backend)     │──→ Переписка
  Facebook Messenger ──→│                         │──→ Консультант бачить
  Viber Bot API ───────→│                         │     все в одному вікні
                        └─────────────────────────┘
```

### Як це працює

1. Людина пише в **Telegram** (або інший месенджер)
2. NestJS отримує повідомлення через Bot API / Webhook
3. Зберігає в БД як `Message` з міткою `channel: 'telegram'`
4. Консультант бачить повідомлення в своєму кабінеті як звичайне
5. Відповідає через веб-інтерфейс
6. NestJS відправляє відповідь назад **в Telegram**

**Людина залишається в Telegram. Консультант залишається в системі.**

### Що бачить консультант

```
┌─────────────────────────────────────────────────────────┐
│  Переписка з Марина              Кейс #247             │
│  Канал: Telegram                                       │
│─────────────────────────────────────────────────────────│
│                                                         │
│  Марина (Telegram):                        14:23        │
│  Привіт, я не можу спати вже тиждень...                │
│                                                         │
│  Наталя (консультант):                     14:35        │
│  Вітаю, Марино. Розкажіть більше...                    │
│                                                         │
│  Марина (Telegram):                        14:38        │
│  Постійна тривога після обстрілів...                   │
│                                                         │
│─────────────────────────────────────────────────────────│
│  [Написати повідомлення...]          [📎] [Надіслати]  │
└─────────────────────────────────────────────────────────┘
```

### Модель даних повідомлення

```
Message {
  id
  careCaseId      → Care Case #247
  senderId        → Марина
  senderRole      → 'person' | 'consultant'
  channel         → 'web' | 'telegram' | 'instagram' | 'facebook' | 'viber'
  channelChatId   → telegram chat id / instagram thread id / ...
  content         → текст повідомлення
  attachments     → файли, фото
  createdAt
}
```

### Сценарії переходу між каналами

**Сценарій 1: Telegram → Сайт**
Людина почала в Telegram, потім зареєструвалась на сайті.
Система зв'язує Telegram-акаунт з веб-акаунтом.
Вся історія переписки доступна і в Telegram, і в кабінеті на сайті.
Людина може продовжити спілкування де зручніше.

**Сценарій 2: Сайт → Telegram**
Людина почала на сайті, потім хоче перейти в Telegram.
В кабінеті кнопка "Продовжити в Telegram".
Переходить до бота → авторизується → чат продовжується.

**Сценарій 3: Тільки Telegram**
Людина пише тільки в Telegram і не хоче реєструватися.
Система веде кейс без веб-акаунту.
Коли/якщо захоче пройти курс → тоді реєстрація.

### Канали — складність підключення

| Канал | API | Складність | Час |
|---|---|---|---|
| Сайт | Socket.io (вже є) | Базова | — |
| Telegram | Bot API + Webhooks | Низька | 1-2 дні |
| Viber | Viber Bot API | Низька | 1-2 дні |
| Instagram | Instagram Messaging API | Середня (потрібна верифікація) | 3-5 днів |
| Facebook | Messenger Platform API | Середня (потрібна верифікація) | 3-5 днів |

### Канали входу (загальна схема)

```
                    ┌──────────────┐
    Сайт ──────────→│              │
    Telegram бот ──→│  Є турбота   │──→ Care Case ──→ Координатор
    Instagram ─────→│   система    │
    Facebook ──────→│              │
    Viber ─────────→│              │
    Реклама ───────→└──────────────┘
```

Людина може написати боту в Telegram → бот задає ті ж питання анкети → створюється кейс → далі консультант може відповідати прямо в Telegram через систему.

### 7.9. Звернення з курсу (Путь Б)

Кнопка **"Поговорити з консультантом"** на кожному уроці. При натисканні — міні-анкета:

```
- Що вас турбує?
  ○ Виникли питання під час курсу
  ○ Потрібна емоційна підтримка
  ○ Хочу поговорити про віру
  ○ Інше
- Наскільки терміново?
  ○ Зараз
  ○ Можу почекати
[Надіслати]
```

Система створює Care Case з контекстом:

```
Care Case #312
├── Людина: Марина, Харків
├── Джерело: курс "Коли тривога не відпускає"
├── Пройдено: 3/8 уроків
├── Тема: емоційна підтримка
├── Терміновість: зараз
└── Статус: нове звернення
```

Координатор бачить **контекст** — який курс, який урок, що могло зачепити. Консультант починає розмову не з нуля.

## 8. Життєвий цикл кейсу

```
Нове звернення
    ↓
Призначено консультанта
    ↓
Перший контакт (переписка)
    ↓
Зустріч запланована
    ↓
Активний супровід ←──── курс паралельно
    ↓                      ↑
    ↓                ще зустрічі
    ↓                      ↑
    ├── Людина відновлюється → Завершено
    ├── Потрібен інший спеціаліст → Передано
    └── Людина не відповідає → Пауза → нагадування
```

## 11. Процесний ризик і автоматизація

### Чому процесний ризик > технічного

Код написати можна. Angular, NestJS, чат, база — це зрозумілі задачі з зрозумілими рішеннями. А ось 30 живих людей — це хаос, якщо немає процесів.

### Конкретні проблеми без автоматизації

**Проблема 1: Хто відповідає?**
Координатор у відпустці → 5 звернень висять без відповіді 2 дні → людина думає, що про неї забули.

**Проблема 2: Нерівне навантаження**
Наталя веде 12 людей і вигорає, Олексій веде 2 і сидить без роботи — бо координатор призначає "кого знає", а не дивиться на навантаження.

**Проблема 3: Консультант зник**
Василь вів 8 людей, захворів на 2 тижні, нікому не передав, не попередив. 8 людей без відповіді. Хто це помітить? Коли?

**Проблема 4: Якість переписки**
Консультант відповідає "Молись і все буде добре" людині в кризі. Хто контролює якість? Хто навчає?

**Проблема 5: Людина в небезпеці**
Марина пише "Я більше не хочу жити" о 23:00. Що робити? Який протокол? Кому ескалювати? Хто чергує?

**Проблема 6: Плинність**
Із 30 волонтерів через 3 місяці: 5 пішли без попередження, 3 відповідають раз на тиждень. Їхні кейси "підвисли" без передачі.

### Рішення: автоматизація процесів

#### 11.1. Авторозподіл звернень (замість ручного координатора)

```
Нове звернення: Марина, тема "тривога", терміново

Система автоматично:
1. Фільтрує консультантів за спеціалізацією → тривога
2. Фільтрує за мовою → українська
3. Фільтрує за доступністю → онлайн або зміна сьогодні
4. Сортує за навантаженням → хто має менше кейсів
5. Призначає → Наталя (тривога, укр, 4/10 кейсів)
6. Надсилає сповіщення Наталі
```

Координатор втручається тільки коли: система не знайшла відповідного, тема нестандартна, або людина в кризі.

#### 11.2. SLA-монітор

```
Звернення без відповіді:
├── > 4 год  → push-сповіщення консультанту
├── > 12 год → повторне сповіщення + email
├── > 24 год → сповіщення координатору + автоперепризначення
└── > 48 год → сповіщення адміну (щось зламалось у процесі)

Переписка без відповіді:
├── > 48 год → нагадування консультанту
├── > 5 днів → сповіщення координатору
└── > 7 днів → статус кейсу → "Пауза", повідомлення людині:
              "Ми помітили, що давно не спілкувались.
               Якщо хочете продовжити — напишіть нам."
```

#### 11.3. Кризовий протокол

```
Марина пише: "Я більше не хочу жити"

Система автоматично:
1. Сканує повідомлення на ключові слова/фрази:
   - "не хочу жити", "суїцид", "покінчити з усім"
   - "мене б'ють", "насильство", "не можу вийти з дому"

2. Визначає рівень ризику:
   - Високий → НЕГАЙНО
   - Середній → протягом 1 години
   - Низький → в порядку черги

3. При ВИСОКОМУ ризику:
   ├── Миттєве сповіщення координатору (push + SMS)
   ├── Сповіщення старшому консультанту
   ├── Автовідповідь людині:
   │   "Ми вас чуємо. Консультант зв'яжеться з вами
   │    якнайшвидше. Якщо вам зараз дуже важко,
   │    зателефонуйте на лінію підтримки: 7333"
   └── Кейс позначається як КРИЗОВИЙ (пріоритет №1)
```

#### 11.4. Контроль навантаження і вигорання

```
├── Ліміт кейсів: макс 10 на консультанта
│   → при 10 система НЕ призначає нових
│
├── Ліміт кризових: макс 3 кризових кейси одночасно
│   → решта — тільки звичайні
│
├── Відпочинок: якщо консультант вів 3+ кризових за тиждень
│   → рекомендація координатору: "Наталі потрібна підтримка"
│
├── Неактивність: консультант не заходив 3+ дні
│   → автосповіщення: "Все добре? У вас 6 активних кейсів"
│   → через 5 днів → перерозподіл кейсів
│
└── Вигорання: середній час відповіді зростає
    → тиждень 1: 2 год → тиждень 4: 18 год
    → система: "Олена, навантаження Наталі зростає.
               Час відповіді збільшився в 9 разів."
```

#### 11.5. Автоматична передача кейсів

```
Консультант натискає "Я йду у відпустку" (або "Я йду"):

1. Показує список його кейсів (6 активних)
2. Пропонує консультантів для заміни (за спеціалізацією + навантаженням)
3. Василь підтверджує або координатор розподіляє
4. Кожна людина отримує повідомлення:
   "Ваш консультант тимчасово недоступний.
    Вас буде супроводжувати Ірина.
    Вся історія збережена."
5. Новий консультант бачить повну історію переписки + нотатки
```

#### 11.6. Автоматичний контроль якості

```
Система відстежує метрики кожного консультанта:
├── Середній час першої відповіді
├── Середній час між повідомленнями
├── Кількість завершених кейсів / місяць
├── % людей, які повернулись після "завершення"
├── Середня довжина супроводу
├── Відгуки людей (після завершення кейсу)
└── Скільки кейсів "зависли" без активності

Щотижневий автозвіт супервізору:
┌─────────────────────────────────────────────────────┐
│  Звіт якості: тиждень 12-18 травня                  │
│                                                     │
│  Потребує уваги:                                    │
│  - Ігор: середній час відповіді 36 год (норма 12)   │
│  - Олексій: 2 кейси без активності > 7 днів         │
│                                                     │
│  Відмінно:                                          │
│  - Наталя: час відповіді 3 год, 4 завершення        │
│  - Ірина: найкращі відгуки (4.8/5)                  │
└─────────────────────────────────────────────────────┘
```

#### 11.7. Автоматичний онбординг нового консультанта

```
Адмін додає нового консультанта → система автоматично:

Тиждень 1: "Навчання"
├── Доступ до бази знань і протоколів
├── Тестовий кейс (бот грає роль людини)
├── Перевірка: чи правильно реагує на кризові фрази
└── Призначення наставника (досвідчений консультант)

Тиждень 2: "Під наглядом"
├── Перші 2-3 реальні кейси
├── Наставник бачить переписку (read-only)
├── Наставник залишає приватні коментарі
└── Ліміт: макс 3 кейси

Тиждень 3+: "Самостійна робота"
├── Ліміт збільшується до 5, потім до 8-10
├── Наставник відключається
└── Звичайний режим
```

### Нова роль: Супервізор

```
Супервізор:
├── Бачить переписки всіх консультантів (read-only)
├── Може залишати приватні коментарі консультанту
│   "Тут краще було б запитати про..."
├── Проводить щотижневі розбори складних кейсів
├── Відповідає за протокол кризових ситуацій
└── Не веде своїх кейсів — тільки контролює
```

### Що автоматизовано vs що залишається людям

| Автоматизовано | Залишається людям |
|---|---|
| Розподіл звернень | Складні/нестандартні кейси |
| SLA-сповіщення | Реальна розмова з людиною |
| Кризова ескалація | Прийняття рішення в кризі |
| Контроль навантаження | Емпатія і душеопікунство |
| Метрики якості | Розбір складних кейсів |
| Передача кейсів | Супервізорська підтримка консультантів |
| Онбординг (базовий) | Менторство нових консультантів |
| Нагадування | Молитва і духовний супровід |

### Як змінюється роль координатора

```
БЕЗ автоматизації:                   З автоматизацією:
Координатор = диспетчер               Координатор = стратег
├── вручну розподіляє ВСЕ             ├── бачить дашборд
├── слідкує за дедлайнами             ├── втручається у винятки
├── нагадує консультантам             ├── підтримує команду
├── перевіряє навантаження            ├── аналізує тренди
└── горить на роботі                  └── планує розвиток
```

### Оновлена таблиця ролей

| Роль | Що бачить | Що може |
|---|---|---|
| **Людина** | Свій кабінет, свого консультанта, свої курси | Писати консультанту, проходити курси, планувати зустрічі |
| **Консультант** | Тільки свої кейси | Вести переписку, нотатки, зустрічі, бачити прогрес курсів |
| **Супервізор** | Переписки всіх консультантів (read-only), звіти якості | Залишати приватні коментарі, проводити розбори кейсів |
| **Координатор** | Дашборд, винятки, аналітика | Ручне призначення у складних випадках, підтримка команди |
| **Адміністратор** | Все | Управління користувачами, курсами, налаштуваннями, автоматизаціями |
