# Бізнес-аналіз — "Є турбота" Care Coordination Platform

## 1. Контекст і мета

- **Що досліджуємо:** Доцільність побудови кастомної Care Coordination Platform для служби духовної опіки з ~30 консультантами-волонтерами
- **Чому зараз:** Служба працює вручну — звернення губляться, консультанти вигорають, кризові ситуації залишаються без протоколу
- **Очікуваний результат:** Обґрунтоване рішення go/no-go з оцінкою ризиків і вартості

---

## 2. Аналіз користувачів

### Цільова аудиторія

**Люди, що шукають допомогу (Person):**
- Вік: 18-65, пік 25-45
- Географія: Україна (80%), діаспора (20%)
- Мова: українська (70%), російська (25%), англійська (5%). Визначити список підтримуваних мов; для непідтримуваних — процедура перенаправлення або залучення перекладача
- Пристрої: 80% мобільні, 20% десктоп
- Основний месенджер: Telegram (60%), Viber (20%), Instagram DM (15%), Facebook (5%), телефон (кризові ситуації — Person може дзвонити по телефону замість чату)
- Технічна грамотність: різна, від низької до високої
- Доступність: Person з інвалідністю може не мати змоги використовувати web-інтерфейс → WCAG 2.1 AA compliance + альтернативні канали (телефон, Telegram)

**Консультанти (душеопікуни):**
- Вік: 25-60
- Мотивація: служіння, волонтерство
- Технічна грамотність: середня
- Працюють: з різних часових зон
- Не мають формальної психологічної освіти (більшість)
- Потребують: простий інтерфейс, чіткі протоколи, підтримку супервізора

### Болі та потреби

| Персона | Біль | Потреба |
|---|---|---|
| Людина | "Нікому до мене діла немає" | Швидка відповідь від живої людини |
| Людина | "Боюсь розповідати стороннім" | Конфіденційність, безпека |
| Людина | "Не хочу встановлювати ще один додаток" | Спілкування через Telegram |
| Консультант | "Я загубився в чатах" | Один інтерфейс для всього |
| Консультант | "Не знаю, що відповісти в кризі" | Протоколи, підтримка супервізора |
| Консультант | "Забагато людей, не встигаю" | Контрольоване навантаження |
| Консультант | "Я вигоряю, але не хочу підводити людей" | Моніторинг навантаження + обов'язкові перерви + супервізія |
| Координатор | "Хто вільний? Хто перевантажений?" | Дашборд навантаження |
| Супервізор | "Не бачу, як веде розмову Ігор" | Read-only доступ до переписок |

### Мотивації

- **Людина:** отримати допомогу, бути почутою, знайти надію
- **Консультант:** служити, допомагати, рости як наставник
- **Координатор:** ефективна команда, жодна людина не загублена
- **Супервізор:** якість допомоги, безпека людей і консультантів

### Поточні рішення (як живуть без нас)

- Координатор веде таблицю в Google Sheets
- Консультанти спілкуються через особисті Telegram-акаунти
- Звернення надходять через Google Forms -> координатор вручну копіює в таблицю -> пише консультанту
- Курси — окремо на YouTube або Google Classroom
- Кризових протоколів немає — "все на довірі"
- Історія переписок — в особистих чатах консультантів, недоступна нікому

## 3. Аналіз процесів

### Як працює зараз (AS-IS)

```
Людина пише в Instagram/Telegram/на сайт
        |
Координатор бачить (якщо не пропустив)
        | (вручну, іноді через 1-2 дні)
Координатор шукає вільного консультанта (в голові або в таблиці)
        | (дзвонить/пише в особистий чат)
Консультант отримує контакт людини
        |
Пише їй в Telegram зі свого акаунту
        |
Переписка + можливо дзвінок через Zoom
        |
Координатор не бачить переписку
Супервізора немає
Статусів немає
Аналітики немає
Усі канали впали одночасно — звернення втрачені
Дублікати звернень через різні канали — одна людина, два консультанти
Два Person з однієї сім'ї з конфліктом — призначені одному консультанту (конфлікт інтересів)
Третя сторона (родич) дзвонить з проханням допомоги для Person — без перевірки згоди
Stalker може створити intake від імені жертви — відсутня верифікація identity
Тренінг для нових консультантів не включає роботу з системою
```

### Що ламається / де втрати

| Точка розриву | Наслідок | Частота |
|---|---|---|
| Координатор пропустив звернення | Людина чекає 2+ дні | 2-3 рази/тиждень |
| Координатор у відпустці | Нові звернення стоять | ~2 тижні/рік |
| Консультант не відповідає | Людина думає, що забута | 3-5 разів/тиждень |
| Консультант вигорає | Якість падає, консультант йде | 2-3 людини/квартал |
| Кризове повідомлення не помічене | Потенційна загроза життю | Рідко, але критично |
| Консультант йде без передачі | 5-10 людей без супроводу | 1-2 рази/квартал |
| Немає історії переписки | Новий консультант починає з нуля | Кожна передача |
| Немає статистики | Неможливо покращувати процес | Постійно |
| Волонтер-консультант не з'являється на зміні | Кейси без нагляду, порушення SLA | Кілька разів/місяць |
| Консультант хворіє раптово | Поточні кейси без нагляду (потребують перерозподілу < 2 год) | Кілька разів/квартал |
| Два Person з конфліктом призначені одному консультанту | Конфлікт інтересів, ризик упередженості | Рідко, але критично |

### Як має працювати (TO-BE)

```
Людина пише через будь-який канал
        | (автоматично, < 1 сек)
Система створює Care Case
        | (автоматично, < 5 сек)
Авторозподіл: спеціалізація -> мова -> навантаження
        | (миттєво)
Якщо консультант підібраний за мовою, але не має доменної експертизи (тема звернення) — застосувати вторинний критерій: тематична спеціалізація / досвід роботи з подібними кейсами. При відсутності збігу — ескалація координатору.
Коли всі консультанти на максимальному навантаженні — нові кейси потрапляють у чергу (queue) з SLA таймером. Person отримує повідомлення про очікування та орієнтовний час.
Persons у черзі отримують проактивне повідомлення з очікуваним часом. Оновлення кожні 30 хв якщо час очікування > 1 год.
Abandonment tracking: якщо Person залишає чергу (закриває чат, не відповідає на ping) — зафіксувати факт abandonment + автоматичний follow-up через N годин (конфігурується координатором, за замовчуванням 4 год) з пропозицією повернутися.
Консультант отримує сповіщення
        | (SLA: перша відповідь < 12 год)
Delivery confirmation для кожного сповіщення консультанту. Якщо підтвердження не отримано протягом 5 хв — автоматичний fallback на альтернативний канал (email → SMS → push). Якщо всі fallback-канали вичерпані і жодне підтвердження не отримано — термінальна ескалація: координатор отримує алерт для ручного зв'язку з консультантом (телефон, особистий контакт).
Переписка в єдиному інтерфейсі
        |
Курс рекомендується автоматично (лише пропозиція — Person може відхилити рекомендацію + залишити feedback чому не підходить; автоматичне зарахування на курс заборонене без явної згоди Person)
        |
Зустріч планується в 2 кліки
        |
Прогрес відстежується
Протокол закриття кейсу: визначені критерії завершення (досягнення цілей, взаємна згода, відсутність активності > 30 днів). Максимальна тривалість кейсу — 6 місяців з можливістю продовження за рішенням супервізора. Періодичний review кожні 4 тижні: консультант оновлює статус, координатор перевіряє прогрес. Автоматичне нагадування при наближенні до max duration.
Кризи виявляються автоматично
Навантаження контролюється
Якість моніториться
        |
Fallback при збої системи: координатор повертається до Google Sheets
Визначити процедуру data sync/export для failover на Google Sheets: автоматичний щоденний export активних кейсів у форматі, сумісному з поточною Google Sheets структурою координатора. Failover export обов'язково включає crisis flag, поточний статус кейсу та пріоритет — щоб кризові кейси не втратили контекст при переході на ручний режим.
Дедуплікація звернень по телефону/email/Telegram ID
Правила fuzzy matching для ідентифікації Person across channels (нормалізація телефону, Levenshtein distance для імен). Manual merge UI для координатора при неоднозначних збігах.
Merge conflict resolution: якщо при злитті виявлено два активні кейси з різними консультантами — координатор отримує алерт з деталями обох кейсів. Правила: (1) пріоритет має кризовий кейс; (2) при рівному пріоритеті — кейс з більшою історією зберігає консультанта; (3) другий консультант отримує повідомлення про закриття дубліката з summary.
Авторозподіл при нульовому збігу: покрокове розширення критеріїв → ескалація координатору
Повторне призначення при порушенні SLA 12 год (з лімітом спроб)
Якщо reassignment вичерпує retry limit і жоден консультант недоступний — кейс ескалюється до координатора з explicit deadline для ручного вирішення.
Crisis detection: false positive → підтвердження людиною; false negative → ручна кнопка "кризис"
Crisis detection у немедійних каналах: голосові повідомлення (voice notes) → speech-to-text → аналіз тексту; зображення → OCR + image classification. Якщо автоматична обробка неможлива — маршрутизація медіа до координатора для ручної оцінки з приоритетом "потенційний кризис".
Fallback при недоступності AI crisis detection: нескоровані повідомлення маршрутизуються до координатора для ручної оцінки. Алерт адміну про AI outage.
Person звертається повторно через рік — старий консультант вже не працює → збереження контексту + призначення нового консультанта з доступом до історії
Preference vs capacity: якщо Person запитує конкретного консультанта, але той на максимальному навантаженні — Person отримує вибір: (1) чекати в черзі на бажаного консультанта з ETA; (2) прийняти іншого доступного консультанта з релевантною спеціалізацією. При кризовому кейсі — preference ігнорується, призначається перший доступний.
Інтеграція телефонії: Person дзвонить по телефону під час кризи замість чату → запис дзвінків з явною згодою, маршрутизація на чергового консультанта
Off-hours телефонія: якщо Person дзвонить поза робочими годинами — IVR з інформацією про екстрені служби (112, гаряча лінія) + можливість залишити голосове повідомлення → callback queue на наступний робочий день. При кризовому IVR-тригері (натиснута кнопка "кризис") — ескалація на нічного чергового (якщо є) або SMS-алерт координатору.
Протокол third-party referral: третя сторона (родич) звертається з проханням допомоги → фіксація звернення, обов'язкове отримання згоди person перед початком роботи
Верифікація identity при intake: захист від створення звернень від чужого імені (stalking) + флаг підозрілого звернення для координатора
Перевірка конфлікту інтересів: перед призначенням перевіряти зв'язки між Person (сім'я, конфлікт) для уникнення призначення одному консультанту
Система підтвердження присутності для зміни: консультант підтверджує готовність перед зміною, при неявці — автоматичний вибір з резервного списку
Протокол екстреного перерозподілу: при раптовій хворобі консультанта — перерозподіл поточних кейсів протягом < 2 годин
Обов'язкові handover notes: при звільненні консультанта — заповнення передавальних нотаток + knowledge base по складних кейсах
Onboarding program: навчання нових консультантів обов'язково включає роботу з системою + менторство
Курс self-help: попередження перед триггерним контентом + можливість пропуску
API для зовнішніх referrals: партнерська організація може направляти клієнтів через API з обов'язковою згодою person
При масштабуванні до 500+ активних кейсів: роль заступника координатора + автоматизація рутинних призначень
```

## 4. SWOT-аналіз

| | Позитивне | Негативне |
|---|---|---|
| **Внутрішнє** | **Сильні сторони:** Унікальна доменна модель (care, не CRM). Повний контроль над UX. Точне вирішення реальних проблем. Можливість масштабування. Дані під повним контролем. TypeScript стек = один розробник може вести frontend і backend | **Слабкі сторони:** Потрібен час на розробку (3-4 міс). Немає готового рішення, все з нуля. Потрібна постійна підтримка. Залежність від розробника. Консультанти-волонтери — нестабільна команда |
| **Зовнішнє** | **Можливості:** Зростаючий попит на психологічну/духовну підтримку. SaaS потенціал для інших організацій. AI для кризового протоколу. Партнерства з церквами, НКО. Грантове фінансування для соціальних проектів. Інтеграція з партнерськими організаціями через API для направлення клієнтів. Розширення на нові регіони (multi-tenant) | **Загрози:** Зміна API месенджерів (Instagram, Facebook). Юридичні ризики (обробка чутливих даних). Волонтери можуть не прийняти нову систему. Залежність від Zoom/Google для відеозустрічей. Зміна законодавства може вимагати зміни процедур обробки даних. Консультант з іншої країни — юрисдикція обробки даних. Організація розширюється на регіон з іншим законодавством. Донори та грантодавці вимагають доступу до даних для звітності |

### ROI оцінка

**Без системи (поточні втрати на рік):**
- ~150 загублених звернень (3/тиждень x 50 тижнів) — люди, які не отримали допомогу
- ~8-10 консультантів, які вигоріли і пішли — втрата досвідчених волонтерів
- ~2-3 кризових ситуації без належної реакції — потенційна загроза
- 0 аналітики — неможливо покращувати процес

**З системою (очікувані покращення):**
- Втрачені звернення: 150 -> <10 (автоматизація)
- Вигорання: 8-10 -> 2-3 (контроль навантаження)
- Кризові без реакції: 2-3 -> 0 (автоматичний протокол)
- Час першої відповіді: 1-2 дні -> <12 годин
