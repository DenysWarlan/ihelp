# E02 — Care Cases

## Мета

Реалізувати повний життєвий цикл кейсу підтримки -- від створення через анкету до закриття, з state machine валідацією переходів, приватними нотатками, audit log та optimistic locking.

## Scope

### Включено

- Створення кейсу з анкети (сайт, Telegram-бот): ім'я, країна, мова, тема, терміновість (CASE-1)
- State machine статусів: new -> assigned -> in_progress -> meeting_scheduled -> on_hold -> completed -> closed (CASE-2)
- Валідація переходів (зворотні заборонено; винятки для координатора та кризового протоколу) (CASE-2)
- Призначення консультанта (авто/ручне) -- інтерфейс; логіка в E06 (CASE-3)
- Приватні нотатки консультанта з перевіркою авторства при редагуванні (CASE-4)
- Audit log дій по кейсу (хто, коли, що змінилося) (CASE-5)
- Зв'язок кейсу з курсом (sourceCourseId, sourceLessonId) (CASE-6)
- Автоматична пауза при неактивності > 7 днів з повідомленням (CASE-7, v1.1)
- Форма відгуку при завершенні (CASE-8, v1.1)
- Теги та категоризація (CASE-9, v1.1)
- Optimistic locking (version field) при одночасному редагуванні (CASE-10)

### Виключено

- Алгоритм авторозподілу (E06 Assignment Engine)
- SLA-таймери та ескалації (E07 SLA Monitor)
- Кризовий протокол та автоматичне переоткриття (E08 Crisis)
- Передача кейсу іншому консультанту (E10 Transfer)
- Чат-повідомлення в рамках кейсу (E03 Chat)

## Критерії приймання

1. Кейс створюється з анкети; перевіряється наявність GDPR-згоди (dataConsentAt NOT NULL)
2. Partial unique index гарантує один активний кейс на Person
3. State machine відхиляє невалідні переходи статусу (400 Bad Request)
4. Координатор/адмін може повернути on_hold -> in_progress
5. Нотатки доступні тільки Staff; редагувати може лише автор
6. Кожна зміна статусу та призначення логується в audit log
7. При одночасному редагуванні другий отримує попередження з пропозицією перезавантажити
8. Кейс, створений через кнопку "Мені важко" в курсі, містить посилання на курс/урок
