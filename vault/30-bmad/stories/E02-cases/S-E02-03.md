# S-E02-03: State machine статусів кейсу

## Контекст
Життєвий цикл кейсу визначає весь робочий процес платформи — від створення звернення до його завершення. Коректні переходи між статусами забезпечують передбачуваність для консультантів та координаторів, а автоматичне переоткриття при кризовому повідомленні є критичним для безпеки людини. SLA-таймери залежать від цієї state machine.

## User Story
Як платформа, я хочу контролювати переходи між статусами кейсу, щоб забезпечити коректний життєвий цикл кожного звернення.

## Критерії приймання
- [ ] AC1: Підтримуються статуси: new → assigned → in_progress → meeting_scheduled → on_hold → completed → closed
- [ ] AC2: Зворотні переходи заборонено — API повертає 400 Bad Request з поясненням
- [ ] AC3: Координатор/адмін може повернути on_hold → in_progress (виняток із загального правила)
- [ ] AC4: Кризове повідомлення до завершеного кейсу — автоматичне переоткриття з ескалацією кризового протоколу
- [ ] AC5: Нове повідомлення до кейсу в статусі on_hold — автоматичний перехід on_hold → in_progress

## Технічні нотатки
- PRD: CASE-2
- State machine pattern (xstate або власна реалізація)
- SLA-таймери НЕ скидаються при зміні статусу
