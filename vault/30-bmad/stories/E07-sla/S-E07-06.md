# S-E07-06: Distributed lock на SLA record

## Контекст
В мікросервісній архітектурі декілька сервісів можуть одночасно оновлювати SLA-запис (наприклад, при паузі кейсу та одночасному надходженні нового повідомлення). Без distributed lock виникає race condition, що може призвести до некоректних SLA-метрик або дублювання ескалацій. Це технічна сторі, яка забезпечує цілісність даних для всіх інших SLA-операцій.

## User Story
Як розробник, я хочу щоб оновлення SLA record було захищене distributed lock, щоб паралельнi оновлення з рiзних мiкросервiсiв не призводили до race condition.

## Критерiї приймання
- [x] AC1: При оновленнi SLA record захоплюється distributed lock (Redis-based)
- [x] AC2: Одночасне оновлення одного SLA record з двох сервiсiв — другий чекає або отримує помилку
- [x] AC3: Lock має TTL (timeout) для запобiгання deadlock при збоях сервiсу
- [x] AC4: При невдалому захопленнi lock — retry з exponential backoff

## Технiчнi нотатки
- Використовувати Redlock алгоритм або Redis SET NX EX
- TTL lock — 5-10 секунд

## Залежностi
